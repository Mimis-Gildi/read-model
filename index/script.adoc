Do you see this PAR number? This is what Google Chrome team can do in the browser.
We treat it as the best possible time. Less time is faster and better.

Here what it looks like. And we will see how:

1: My pure TypeScript Optimized Fixture – this is "best performance" over pure DOM manipulation.

2: React, competently written, competing for the same thing. A completely different architecture!
Data driven information presentation diffing two DOMs. I used all the key elements of React architecture:

* State by Zustand, one global store – so folding a hundred teams is ONE update, ONE reconciliation,
 not a hundred.
* React.memo on every node – without it, one toggle re-renders the whole tree. With it, only the node
 that changed re-renders.
* Per-id selectors – each row subscribes to its OWN fold flag only. Touch one team, only that team
 re-renders. This is React's own prescribed pattern for fine-grained reactivity.
* flushSync – React normally defers commits. Without this, my "time after render" lies to you. This
 makes the clock honest.
* Folded kids are UNMOUNTED, not hidden with CSS. Same rule Pure TS plays by: a fold costs a real
 unmount, a reveal costs a real mount, reconcile, and paint. No cheating the benchmark with display:none.
* Clean teardown between rungs – unmount the root, recreate it. The next build is a fresh mount, never
 a diff against yesterday's ghost.

What I did NOT use, and why:

* No useEffect – every state change here is driven directly by the benchmark harness, not by lifecycle.
 An effect adds a tick the clock can't afford.
* No useMemo / useCallback – React.memo already scopes the re-render. Memoizing callbacks on top buys
 nothing and costs cycles.
* No Context – Zustand already reaches any component directly. Context here is a redundant pipe.
* No local useState – all state is shared, so local state would just duplicate the store.
* No Suspense, no lazy loading – this is a synchronous, clocked benchmark. Async boundaries break the
 "block until commit" contract the whole measurement depends on.

So when people tell me "you don't know React" – I used the architecture EXACTLY as its own team
prescribes for performance. I'm a hacker: I read source before using a framework, not hype articles.
Selectors, memo, batched updates, real mount cost. No shortcuts, no bypass, no cheating.
*If React loses here, it loses playing its A-game.*

3: Last but not least – world's most elegant, smart, and enjoyable technology – pure SONG!
Composable on top of the most pragmatic language ecosystem. And fo all that MAGIC it comes with
a staggering cost – it drags in the Entire Android JetPack Core. Let's see if the cost is worth it.

Same rule applies – I used Compose the way ITS OWN team prescribes for control, not the lazy default:

* MutableState per fold, not one big state object – `remember { mutableStateOf(...) }` per node, so
 toggling one team only invalidates that node's snapshot, nobody else's.

* Manual snapshot + recompose, not `setContent`'s automatic recomposition – I take a mutable snapshot,
 record exactly which states changed, recompose, apply. That's Compose's OWN low-level API for
 "recompose only what I touched, and let me clock the boundary myself."

* Folded kids never emitted into the tree at all – `if (children.isNotEmpty() && !closed)` – same
 unmount-cost rule as React and Pure. No CSS hiding here either.

* Clean teardown – dispose the composition, clear the fold registry, replace the host's children.
 Next build starts from zero, same discipline as the other two.

What I did NOT use, and why:

* No `setContent` – that's Compose's convenience entrypoint with its own scheduler; it would hide the
 recompose boundary I need to clock honestly.

* No Compose Web's built-in event/attr DSL sugar beyond what's needed – I skip layers that don't affect
 measured cost, keep the DOM shape identical to Pure and React so all three build the exact same tree.

* No coroutines / LaunchedEffect – this is synchronous and clocked, same reason as no useEffect in React.

So this isn't "Compose out of the box" – it's Compose with its own snapshot system driven by hand,
the same care I gave React. *All three fixtures get the SAME rule: use the framework's prescribed
performance path, or don't claim to have tested the framework at all.*
